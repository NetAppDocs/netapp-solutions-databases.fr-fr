[role="lead"]
Déployez SQL Server 2025 sur Windows Server 2025 avec des bases de données utilisateur, des journaux de transactions, TempDB et des sauvegardes sur des partages SMB 3 à disponibilité continue sur un système AFF NetApp. Cette procédure comprend la configuration de la SVM ONTAP, des volumes et des partages, l'installation de SQL Server et la protection des bases de données avec SnapCenter.



[[scope]]
[[intro-scope]]
== Portée

Cette procédure déploie une instance SQL Server 2025 autonome sur un seul hôte Windows Server 2025, avec les bases de données utilisateur, les journaux de transactions, TempDB et les sauvegardes sur des partages SMB 3 à disponibilité continue (CA). La même architecture de stockage s'applique aux instances de cluster de basculement SQL Server (FCI) et aux groupes de disponibilité Always On, mais leur configuration spécifique au cluster n'est pas couverte. L'optimisation des performances et le dimensionnement de SQL Server ne sont pas non plus couverts. Pour connaître les avantages, les composants de la solution, les principes de conception et le fonctionnement de la disponibilité continue, consultez link:sql-smb3-aff-overview.html["Découvrez SQL Server 2025 sur NetApp AFF avec disponibilité continue SMB 3"].



[[audience]]
[[intro-audience]]
== Public

Cette procédure est destinée à :

* *Administrateurs de stockage*, qui configurent le cluster ONTAP, la SVM, les volumes et les partages SMB.
* *Administrateurs Windows et Active Directory*, qui préparent l'hôte Windows Server 2025, les comptes de service et le réseau.
* *Administrateurs de bases de données*, qui installent et configurent SQL Server 2025 et mettent en place la sauvegarde et la restauration.


Une connaissance de base de l'administration de ONTAP System Manager, de Windows Server et de SQL Server est requise.

TIP: Utilisez des volumes distincts pour les données, les journaux, TempDB et les sauvegardes. Cela vous permet d'appliquer des paramètres de QoS, de snapshots, d'efficacité et de réplication différents à chaque volume. De plus, TempDB, qui évolue constamment, reste exclu des snapshots de vos bases de données utilisateur.



[[prerequisites]]
== Prérequis

Veuillez vous assurer que les conditions suivantes sont remplies avant de commencer :

.NetApp ONTAP
* La paire haute disponibilité AFF est installée, et le cluster est configuré et en bonne santé.
* La licence CIFS (SMB) est installée. Elle est incluse dans ONTAP One.
* Il existe au moins un agrégat de données (niveau local) sur chaque nœud.
* La synchronisation de l'heure entre le cluster et Active Directory s'effectue via NTP. Le décalage horaire maximal autorisé pour Kerberos est de 5 minutes.
* Les ports du réseau de données, le domaine de diffusion et (en option) les VLAN pour les LIF SMB sont configurés.


.Active Directory et DNS
* Un domaine Active Directory est disponible et les serveurs DNS sont accessibles depuis les LIF de données du SVM.
* Vous disposez d'un compte autorisé à créer des objets d'ordinateur dans l'unité d'organisation cible, pour le serveur CIFS.
* Un compte utilisateur de domaine dédié peut être utilisé comme compte de service pour les services SQL Server Database Engine et SQL Server Agent.



IMPORTANT: SQL Server doit s'exécuter sous un compte de domaine lorsque ses fichiers se trouvent sur un partage SMB. Les comptes virtuels intégrés (`NT SERVICE\MSSQLSERVER`) et les comptes locaux ne peuvent pas se voir accorder l'accès à un partage de fichiers distant.

.Windows Server
* Windows Server 2025 (Desktop Experience) est installé, mis à jour et joint au domaine.
* Le support d'installation de SQL Server 2025 (ISO) et une clé de produit valide (ou une édition gratuite) sont disponibles.


.Exigences et restrictions SMB pour SQL Server sur ONTAP
* Le protocole SMB 3.0 ou une version ultérieure doit être activé sur la SVM.
* Tous les volumes hébergeant des partages CA doivent utiliser le style de sécurité *NTFS* et doivent avoir été en *NTFS* dès le départ.
* SMB Direct (RDMA) n'est pas pris en charge.
* ReFS n'est pas pris en charge. ONTAP (WAFL) fournit le système de fichiers pour les partages.

+
.Afficher un exemple
[%collapsible]

image:sql25_smb_bp_007.png["Ajouter une machine virtuelle de stockage - nom et protocole"]

TIP: Une interface logique (LIF) par nœud permet à SQL Server d’accéder directement (localement) à chaque nœud. C’est une condition préalable au protocole SMB multicanal et au basculement sans interruption de service. Utilisez des ports 25 GbE ou plus rapides et une MTU identique de bout en bout.

+

NOTE: Vous devez enregistrer ces interfaces réseau auprès de votre serveur DNS. Pour plus de détails, consultez https://docs.netapp.com/us-en/ontap-system-manager-classic/smb-config/task_mapping_smb_server_dns_server.html["Associer le serveur SMB au serveur DNS"^].

.. Vérifiez le volume racine du SVM (`a50_sql_root` dans le laboratoire). Il doit utiliser le style de sécurité *NTFS*, sinon les partages SMB ne fonctionneront pas. Accédez à menu:Storage[Volumes], sélectionnez le volume racine et cliquez sur *Edit* pour vérifier ses paramètres.
+
.Afficher un exemple
[%collapsible]
=====
image:sql25_smb_bp_012.png["Modifier le volume racine SVM a50_sql_root"]

=====


--
.ONTAP CLI
--
Les commandes suivantes permettent de créer la même configuration depuis l'interface de ligne de commande. Remplacez les valeurs d'espace réservé entre chevrons.

[source, console]
----
cluster::> vserver create -vserver a50-sql -rootvolume a50_sql_root -aggregate <aggr_node1> -rootvolume-security-style ntfs

cluster::> vserver modify -vserver a50-sql -allowed-protocols cifs

cluster::> network interface create -vserver a50-sql -lif a50-sql_smb_n1 -service-policy default-data-files -home-node <node1> -home-port <port> -address 192.168.175.138 -netmask <netmask>
cluster::> network interface create -vserver a50-sql -lif a50-sql_smb_n2 -service-policy default-data-files -home-node <node2> -home-port <port> -address 192.168.175.139 -netmask <netmask>

cluster::> vserver services name-service dns create -vserver a50-sql -domains sapcc.stl.netapp.com -name-servers <dns1>,<dns2>

cluster::> vserver cifs create -vserver a50-sql -cifs-server A50-SQL -domain sapcc.stl.netapp.com -ou CN=Computers
----
--
====
. [[svm-smb-options,Configurer les options du serveur SMB]]Configurez les options du serveur SMB. Vérifiez que les options SMB requises pour SQL Server sont activées sur la SVM :
+
[source, console]
----
cluster::> set -privilege advanced
cluster::*> vserver cifs options show -vserver a50-sql -fields smb3-enabled,is-multichannel-enabled,is-large-mtu-enabled,copy-offload-enabled,shadowcopy-enabled
cluster::*> vserver cifs options modify -vserver a50-sql -smb3-enabled true -is-multichannel-enabled true -is-large-mtu-enabled true -copy-offload-enabled true -shadowcopy-enabled true
cluster::*> set -privilege admin
----
+
[cols="1,3"]
|===
| Option | But 


| `smb3-enabled` | SMB 3.x est requis pour les partages disponibles en permanence. 


| `is-multichannel-enabled` | Le protocole SMB multicanal utilise plusieurs connexions TCP et chemins réseau pour un débit et une résilience accrus. 


| `is-large-mtu-enabled` | Autorise les lectures et écritures SMB jusqu'à 1 Mo. 


| `copy-offload-enabled` | Déchargement de copie ODX ; les copies sont effectuées à l’intérieur du système de stockage. 


| `shadowcopy-enabled` | VSS distant pour les partages SMB. Requis par les applications de sauvegarde qui utilisent VSS pour les partages SMB. 
|===

[role="tabbed-block"]
====

--

+
.Afficher un exemple
[%collapsible]

image::sql25_smb_bp_025.png[Liste des partages SMB]

=====
.. Cliquez sur l'icône Plus d’options (*⋮*) à côté du partage `sql1_data` et sélectionnez *Modifier*.
+
.Afficher un exemple

+
*** *Activer la disponibilité continue*: *sélectionné*
*** *Autoriser les clients à accéder au répertoire des snapshots* : désactivé
*** *Chiffrer les données lors de l’accès à ce partage* : décoché (facultatif, selon vos exigences de sécurité)
*** *Activer les oplocks* : sélectionné
*** *Activer la notification de changement* : sélectionné

+
Cliquez sur *Enregistrer*.

[[step-6-prepare-windows-server-2025]]
[[windows-prep]]
== Étape 6 : Préparer Windows Server 2025

Effectuez les étapes suivantes sur l'hôte SQL Server `{host}` en tant qu'administrateur de domaine.

.Étapes
. Vérifiez que le serveur est joint au domaine et que le serveur CIFS peut être résolu (voir <<svm-smb-options>>).
. Assurez-vous que le compte de service SQL Server existe dans Active Directory, par exemple `SAPCC\sql1admin`. Utilisez le même compte pour le moteur de base de données et pour SQL Server Agent, ou utilisez un compte distinct pour chacun. Dans tous les cas, accordez à chaque compte l'accès aux quatre partages.
. Tester l'accès aux partages dans le contexte de sécurité du compte de service :
+
[source, powershell]
----
PS C:\> runas /user:SAPCC\sql1admin "cmd /c dir \\a50-sql\sql1_data && echo test > \\a50-sql\sql1_data\write-test.txt && del \\a50-sql\sql1_data\write-test.txt"
----
. Ouvrez le port SQL Server dans le pare-feu Windows :
+
[source, powershell]
----
PS C:\> New-NetFirewallRule -DisplayName "SQL Server (TCP 1433)" -Direction Inbound -Protocol TCP -LocalPort 1433 -Action Allow
----
. Vérifiez la connexion SMB à la SVM. Le dialecte doit être 3.x et `ContinuouslyAvailable` doit être `True`:
+
[source, powershell]
----
PS C:\> dir \\a50-sql\sql1_data | Out-Null
PS C:\> Get-SmbConnection -ServerName a50-sql | Format-Table ServerName,ShareName,Dialect,ContinuouslyAvailable,Encrypted,Signed
PS C:\> Get-SmbMultichannelConnection -ServerName a50-sql
----



NOTE: Par défaut, Windows Server 2025 exige la signature SMB pour toutes les connexions SMB sortantes. ONTAP prend en charge la signature SMB et la négocie automatiquement. La signature engendre une charge CPU supplémentaire des deux côtés ; il est donc important de l’inclure dans vos tests de performance. Ne désactivez pas la signature sans avoir préalablement effectué une analyse de sécurité.

[[use-an-ontap-cli-script-to-configure-the-storage-in-one-pass]]
== Utilisez un script CLI ONTAP pour configurer le stockage en une seule fois

Le script suivant contient la configuration de stockage complète de cette procédure. Remplacez les valeurs entre chevrons avant de l'exécuter.

[source, console]
----
# --- SVM -----------------------------------------------------------------
vserver create -vserver a50-sql -rootvolume a50_sql_root -aggregate <aggr_node1> -rootvolume-security-style ntfs
vserver modify -vserver a50-sql -allowed-protocols cifs

network interface create -vserver a50-sql -lif a50-sql_smb_n1 -service-policy default-data-files -home-node <node1> -home-port <port> -address 192.168.175.138 -netmask <netmask>
network interface create -vserver a50-sql -lif a50-sql_smb_n2 -service-policy default-data-files -home-node <node2> -home-port <port> -address 192.168.175.139 -netmask <netmask>

vserver services name-service dns create -vserver a50-sql -domains sapcc.stl.netapp.com -name-servers <dns1>,<dns2>
vserver cifs create -vserver a50-sql -cifs-server A50-SQL -domain sapcc.stl.netapp.com -ou CN=Computers

set -privilege advanced
vserver cifs options modify -vserver a50-sql -smb3-enabled true -is-multichannel-enabled true -is-large-mtu-enabled true -copy-offload-enabled true -shadowcopy-enabled true
set -privilege admin

# --- Volumes -------------------------------------------------------------
volume create -vserver a50-sql -volume sql1_data    -aggregate <aggr_node1> -size 1TB   -security-style ntfs -junction-path /sql1_data    -space-guarantee none -fractional-reserve 0 -percent-snapshot-space 5 -snapshot-policy none -autosize-mode grow -max-autosize 1.3TB
volume create -vserver a50-sql -volume sql1_log     -aggregate <aggr_node2> -size 512GB -security-style ntfs -junction-path /sql1_log     -space-guarantee none -fractional-reserve 0 -percent-snapshot-space 5 -snapshot-policy none -autosize-mode grow -max-autosize 650GB
volume create -vserver a50-sql -volume sql1_tempdb  -aggregate <aggr_node2> -size 500GB -security-style ntfs -junction-path /sql1_tempdb  -space-guarantee none -fractional-reserve 0 -percent-snapshot-space 0 -snapshot-policy none -autosize-mode grow -max-autosize 650GB
volume create -vserver a50-sql -volume sql1_backups -aggregate <aggr_node1> -size 2000GB -security-style ntfs -junction-path /sql1_backups -space-guarantee none -fractional-reserve 0 -percent-snapshot-space 5 -snapshot-policy none -autosize-mode grow -max-autosize 2600GB

# --- CA shares -----------------------------------------------------------
vserver cifs share create -vserver a50-sql -share-name sql1_data    -path /sql1_data    -share-properties oplocks,browsable,changenotify,continuously-available
vserver cifs share create -vserver a50-sql -share-name sql1_log     -path /sql1_log     -share-properties oplocks,browsable,changenotify,continuously-available
vserver cifs share create -vserver a50-sql -share-name sql1_tempdb  -path /sql1_tempdb  -share-properties oplocks,browsable,changenotify,continuously-available
vserver cifs share create -vserver a50-sql -share-name sql1_backups -path /sql1_backups -share-properties oplocks,browsable,changenotify,continuously-available

# --- Share permissions (repeat for each share) ----------------------------
vserver cifs share access-control create -vserver a50-sql -share sql1_data -user-or-group SAPCC\sql1admin -permission Full_Control
vserver cifs share access-control delete -vserver a50-sql -share sql1_data -user-or-group Everyone

# --- Verification ----------------------------------------------------------
vserver cifs show -vserver a50-sql
vserver cifs share show -vserver a50-sql -fields share-name,path,share-properties
vserver cifs session file show -vserver a50-sql -fields share,path,continuously-available
----

TIP: Répartissez les volumes entre les agrégats des deux nœuds, par exemple les données et les sauvegardes sur le nœud 1, et les journaux et TempDB sur le nœud 2. Cela utilise les ressources des deux contrôleurs.
